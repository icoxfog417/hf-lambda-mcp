# Hugging Face のモデルをワンクリックでサーバーレス MCP に ── PLaMo 3 Translate を AWS Lambda + AgentCore Gateway で動かす

> English version: [serverless-hf-mcp.en.md](serverless-hf-mcp.en.md)（この記事を、記事で紹介している仕組みそのもの = PLaMo 3 Translate の `translate_file` で翻訳しました）

Claude Opus のような高性能モデルは、翻訳も当然こなします。ただ、長いドキュメントの翻訳を任せると、出力トークンを大量に消費して時間もコストもかかります。翻訳のように「やることは明確だが量が多い」作業は、専用の小さなモデルに任せるのが合理的です。

そこで、Preferred Networks（PFN）が公開した翻訳特化モデル [PLaMo 3 Translate](https://www.preferred.jp/ja/blog/tech/plamo-3-translate-weight-release) を **AWS Lambda 上で動かし、MCP ツールとして Claude Code などのエージェントから呼び出せるようにする** 仕組みを作りました。CloudFormation のボタン 1 つでデプロイでき、使っていない間は費用がかかりません。

さらに、PLaMo 専用のコードは書いていません。モデルごとの設定は YAML ファイル 1 枚にまとめ、**Hugging Face 上の別のモデルにも同じ仕組みを使い回せる**ようにしています。

- リポジトリ: https://github.com/icoxfog417/hf-lambda-mcp
- ライセンス: Apache-2.0（ホスティング用のコードのみ。モデルの重みは含みません）

この記事では次の 3 点を紹介します。

1. 作ったものと使い方
2. 裏側の仕組み: アーキテクチャと、ローカルの MCP からリモートまでの通信経路
3. 工夫したこと・学んだこと: ECR と EFS の選択、モデル非依存の設計、コールドスタートとの格闘など

## 1. 作ったもの: hf-lambda-mcp

### できること

| ツール | 動作する場所 | 内容 |
|---|---|---|
| `translate` | AgentCore Gateway (リモート) | テキストを翻訳する。`target_lang`、`source_lang`、`context`（訳語の判断に使う参考文）、`glossary`（用語集）、`form`（日本語の文体: です・ます / だ・である）を指定できる |
| `translate_file` | ローカルクライアント | ローカルの `.md` / `.txt` ファイルを翻訳し、`<ファイル名>.<言語>.md` として元ファイルの隣に保存する |
| `get_model_info` | AgentCore Gateway | 使っているモデル、リビジョン、ライセンスを返す |

`translate_file` のポイントは、**ファイルの中身がエージェントのコンテキストを通らない**ことです。エージェントが受け取るのは保存先のパスと統計情報だけです。Markdown のフロントマター、コードブロック、HTML コメント、数式ブロックは一切変更せず、本文だけを翻訳します。

### 使い方

**① デプロイ**

README の **Launch Stack** ボタンから CloudFormation コンソールを開き、パラメータを確認して作成します。

| パラメータ | 既定値 | 説明 |
|---|---|---|
| `ModelProfile` | `plamo-3-translate` | `profiles/` 配下のプロファイル名 |
| `ModelVariant` | `2b` | `0.8b`（最速）/ `2b`（推奨）/ `8b` |
| `Architecture` | `arm64` | 計測した範囲では x86_64 より 1.5〜2.4 倍速い |
| `MaxParallelSegments` | `8` | 1 つのドキュメントを何並列で処理するか |
| `EnableSnapStart` | `false` | コールドスタートを短くする代わりに待機中も課金される（後述） |

完了まで 20〜30 分ほどかかります。モデルの重みは、デプロイ時に**あなたのアカウント内で** Hugging Face からダウンロードされます。

**② エージェントにつなぐ**

スタックの出力 `ClientCommand` を、そのまま MCP サーバーとして登録します。

```bash
claude mcp add plamo-translate -- \
  uvx --from git+https://github.com/icoxfog417/hf-lambda-mcp.git@main \
  hf-lambda-mcp https://<gateway-id>.gateway.bedrock-agentcore.us-east-2.amazonaws.com/mcp
```

認証には、手元の AWS 認証情報（AWS CLI と同じもの）を使います。管理者以外が使う場合は、出力 `GatewayArn` に対する `bedrock-agentcore:InvokeGateway` 権限を付与します。

**③ 使う**

> docs/guide.md を plamo-translate で英語に翻訳して

と頼むと、エージェントは `translate_file(input_path="docs/guide.md", target_lang="en")` を呼び出し、`docs/guide.en.md` が作成されます。

実際の応答例です（arm64、2B モデル、ウォーム状態）。

```text
translate ja->en        1.9s  "The meeting has been rescheduled for next Monday."
translate en->ja        1.9s  「スタックをデプロイし、エージェントをゲートウェイに接続してください。」
                              （form=polite、glossary: stack→スタック, gateway→ゲートウェイ）
target_lang="EN"        1.2s  isError: invalid arguments: target_lang must use lowercase language codes ...
translate_file (18KB)  54.6s  5 セグメントを並列処理。行構造は原文と一致、未翻訳の行は 0
```

18KB の Markdown ファイルの翻訳にかかった Lambda の料金は、コールドスタートを含めて **約 0.024 ドル** でした（1,818 GB 秒）。

## 2. 裏側: アーキテクチャと通信経路

### 全体像

```
 ┌──────────────┐  stdio   ┌─────────────────┐  HTTPS + SigV4    ┌───────────────────┐  Invoke   ┌──────────────────────────┐
 │ Claude Code  │◄────────►│ hf-lambda-mcp   │◄─────────────────►│ AgentCore Gateway │──────────►│ Lambda (コンテナイメージ)  │
 │ など         │  (MCP)   │ ローカル        │ (MCP Streamable   │  (AWS_IAM 認証)   │ (Gateway  │  ├ llama-server           │
 └──────────────┘          │ クライアント    │  HTTP)            └───────────────────┘  の IAM   │  │  127.0.0.1:18080       │
                           │ (uvx)           │                                          ロール)  │  └ GGUF モデル            │
                           └───────┬─────────┘                                                   └────────────┬─────────────┘
                                   │ 署名付き URL で PUT / GET                                                │ 非同期の自己呼び出し
                                   └────────────────────────►  S3 (uploads/ results/ jobs/ は 1 日で削除) ◄──────┘  (並列ワーカー)
```

### 通信経路を順に追う

**① エージェント ⇔ ローカルクライアント（stdio）**

Claude Code は `uvx` で起動した `hf-lambda-mcp` と、標準入出力で MCP 通信します。このクライアントは [mcp-proxy-for-aws](https://github.com/aws/mcp-proxy-for-aws) の代わりになるもので、内部では同ライブラリの `aws_iam_streamablehttp_client` を使って SigV4 署名を付けています。

**② ローカルクライアント ⇔ AgentCore Gateway（HTTPS + SigV4）**

Gateway の受信側の認証は `AWS_IAM` です。当初は Cognito による OAuth も検討しましたが、Cognito は MCP クライアントが必要とする動的クライアント登録（DCR / CIMD）に対応していないため、IAM を採用しました。ツール名は Gateway によって `<ターゲット名>___<ツール名>` という形になるので、ローカルクライアントが接頭辞を外して `translate` として見せています。

**③ Gateway ⇔ Lambda（IAM ロールで Invoke）**

Gateway は、ツールの引数をそのままイベントとして Lambda に渡します。呼び出されたツール名は `context.client_context.custom["bedrockAgentCoreToolName"]` に入っています。ツールのスキーマは、ビルド時にプロファイルから生成して S3 に置き、ターゲット定義からはその S3 の URI を参照します。

**④ Lambda 内部**

Lambda の初期化フェーズで llama.cpp の `llama-server` を子プロセスとして起動し、ハンドラは `127.0.0.1:18080` の OpenAI 互換 API を呼び出します。8080 番ポートは、ローカルで動かす Lambda エミュレータ（RIE）と衝突するため避けました。

**⑤ ファイル翻訳の経路**

`translate_file` を呼ぶと、次の流れで処理されます。

1. `create_upload` で S3 への署名付き PUT URL を取得し、ローカルクライアントがファイルを直接アップロードする（利用者は S3 の権限もバケットも用意しなくてよい）
2. `start_job` を呼ぶと、Lambda が自分自身を非同期で呼び出して「計画担当」のワーカーを起動する
3. 計画担当がドキュメントを分割し、最大 8 個の「セグメント担当」ワーカーを並列に起動する
4. 各ワーカーはチャンクを 1 つ処理するたびに進捗を S3 に保存する。残り時間が少なくなったら状態を保存して自分を呼び直すので、Lambda の 15 分制限を超える長さでも処理できる
5. 最後に終わったワーカーが全体を組み立て、`results/` に保存する
6. ローカルクライアントは `get_job` をポーリングして MCP の進捗通知を送り、完了したら署名付き GET URL から結果をダウンロードして保存する

### デプロイの流れ（ワンクリックの中身）

```
CloudFormation
 ├─ S3 / ECR / CodeBuild / ビルド調整用の Lambda を作成
 ├─ カスタムリソース ModelImage ─► CodeBuild を起動（CloudFormation への応答 URL を環境変数で渡す）
 │     CodeBuild: リポジトリを取得 → プロファイルを解決 → Hugging Face からモデルを取得
 │               → llama.cpp をビルド → イメージを ECR へ push → ツールのスキーマを S3 へ
 │     EventBridge (ビルド完了) ─► 調整用 Lambda ─► CloudFormation に SUCCESS / FAILED を返す
 ├─ Lambda 関数 / バージョン / エイリアス `live`
 ├─ カスタムリソース WarmUp ─► 新しいバージョンを 1 回呼び出す（モデルを読み込めなければデプロイを失敗させる）
 └─ AgentCore Gateway (AWS_IAM) + Lambda ターゲット
```

参考にした [ndl-ocr-lite-lambda](https://github.com/icoxfog417/ndl-ocr-lite-lambda) では、CodeBuild の中で CDK を実行していました。いまは **AgentCore Gateway がネイティブの CloudFormation リソース**（`AWS::BedrockAgentCore::Gateway` / `GatewayTarget`）として使えるので、テンプレート 1 枚で完結させました。ビルドの成否は EventBridge 経由で CloudFormation に返すので、どのフェーズで失敗しても、ログへのリンク付きでスタックがロールバックされます。

## 3. 工夫したこと・学んだこと

### 3.1 モデル非依存の設計: 「モデルカードを二重に書かない」

Hugging Face のモデルごとにリポジトリを作るのは避けたいところです。かといって汎用化しすぎると、エージェントにとって使いにくいツールになります。そこで、**モデルの成果物から機械的に読み取れることは読み取り、読み取れないことだけをプロファイルに書く**という線引きをしました。

| 必要な情報 | 情報源 | プロファイルに書くか |
|---|---|---|
| プロンプト形式 | `chat_template.jinja`（または GGUF に埋め込まれたテンプレート）。llama-server に `--jinja` でそのまま渡す | 不要 |
| パラメータ名 | チャットテンプレートが参照している変数（`target_lang`、`glossary` など） | 不要（ビルド時に照合する） |
| 入力の検証 | テンプレート内の `raise_exception()` | 不要 |
| コンテキスト長 | GGUF のメタデータ | 不要 |
| ライセンス | Hugging Face のモデルカードのメタデータ | 不要 |
| エージェント向けのツール説明と型 | モデルカードの本文（人間向けの文章） | **必要** |
| どのサイズ・量子化のファイルを使うか | デプロイ時の判断 | **必要** |
| ドキュメント処理の設定 | このプラットフォームの機能 | **必要** |

PLaMo のプロファイルは、ほぼツールの説明文だけになりました。

```yaml
name: plamo-3-translate
source:
  repo: pfnet/plamo-3-translate-{variant}-GGUF
  file: plamo-3-translate-{variant}-Q4_K_M.gguf
  variants: [0.8b, 2b, 8b]
  default_variant: 2b
generation: {temperature: 0}
tools:
  - name: translate
    description: Translate text with PLaMo 3 Translate ...
    input: {name: text, description: Source text to translate}
    params:            # 名前はチャットテンプレートの変数と照合される
      target_lang: {type: string, required: true, description: ...}
      glossary:    {type: array, description: ..., items: {...}}
      form:        {type: string, enum: [plain, polite], description: ...}
    document: {formats: [txt, md], max_chunk_tokens: 512, history: 1,
               output_name: "{stem}.{target_lang}{ext}"}
```

うまくいったと感じた点が 3 つあります。

- **入力検証をモデル側に任せられる**: PLaMo のテンプレートは、言語コードの形式や「`form` は日本語出力のときだけ指定できる」といった条件を自分で検証しています。そのエラーメッセージをそのままツールのエラーとして返すと、エージェントはそれを読んで引数を自分で直します。検証コードを一行も書かずに済みました。
- **レスポンスの設定はいらなかった**: 「レスポンスの形式も定義すべきか」という議論もしましたが、出力はアシスタントの返答テキストだけで十分でした。モデルカードには PLaMo 固有の制御トークンを追加の停止トークンとして指定する例がありますが、実際には EOS トークンで正しく止まり、設定は不要でした。
- **テンプレート変数の抽出には一工夫が必要**: `jinja2.meta.find_undeclared_variables` の結果には、テンプレート内のマクロでローカルに `set` している変数も含まれてしまいます。そこで代入されている変数を除外しつつ、`{% if target_lang is not defined %}` のように「定義されているか」を調べている変数は呼び出し側から渡す引数として扱う、という処理を入れました。

### 3.2 ECR か EFS か: 本当の制約はイメージサイズではない

参考実装では、ONNX モデルを EFS に置いていました。今回も「コンテナイメージの上限は 10GB なので、大きなモデルは収まらないのでは」という懸念がありました。しかし整理してみると、ボトルネックは別のところにありました。

- **Lambda のメモリ上限も 10GB**: モデルと KV キャッシュはメモリに載せる必要があります。つまり 10GB のイメージに収まらないモデルは、EFS に置いても Lambda では動きません。
- **モデル以外の部分は小さい**: すべての CPU 向けバリアントを含めても、llama.cpp は **71MB** でした。Python のベースイメージを含めても、モデル以外は約 0.65GB です。
- **実用的なのはもっと小さいモデル**: CPU での推論速度はおおよそモデルサイズに反比例します。実際に使えるのは 3〜5GB 以下のモデルです。
- **EFS には別のコストがある**: VPC が必要になり、EFS にモデルを配置するための仕組みも必要です。コールドスタートのたびにネットワーク越しの読み込みも発生します。

結論として、**モデルをイメージに焼き込んで ECR に置く**方式にしました。もっと大きなモデルを使いたくなったら、EFS ではなく GPU を使える実行環境（AgentCore Runtime や SageMaker など）を同じ Gateway の後ろにつなぐのが筋だと考えています。

### 3.3 コールドスタートとの格闘: 415 秒 → 数十秒

最初に計測したとき、2B モデルのコールドスタートは **415 秒** でした。

原因は、Lambda がコンテナイメージを必要な部分から順に取得する遅延読み込みと、llama.cpp の mmap（必要なページを飛び飛びに読み込む）の相性が悪いことでした。ランダムに発生するページフォールトの一つひとつが、遅延読み込みの遅さに直撃していたのです。

| 対策 | コールドスタート | 待機中のコスト |
|---|---|---|
| 何もしない（mmap で直接読み込む） | 約 415 秒 | なし |
| **モデルファイルを複数スレッドで先頭から順に先読みしてから llama-server を起動する**（既定） | **数秒〜80 秒**（Lambda のイメージキャッシュの状態による） | なし |
| SnapStart（モデル読み込み後のスナップショットから復元） | 約 11 秒（復元自体は 2.2 秒） | **10GB の設定で月 40 ドル程度** |

ここで学んだことが 3 つあります。

- **SnapStart はコンテナイメージにも使えるようになったが、待機中も課金される**: 子プロセスの llama-server ごとスナップショットから復元でき、効果は劇的でした。ただし Python のイメージでは、スナップショットのキャッシュ料金（GB 秒あたり 0.0000015046 ドル）がかかります。10GB のメモリ設定では、使っていなくても月 40 ドル前後になります。「使わないときは 0 円」という目的とは相容れないので、オプションにしました。
- **シンプルな先読みがよく効く**: mmap より前に、モデルファイルを 16MB 単位で 8 スレッドから順に読むだけです。これだけで 415 秒が数十秒になりました（実装は 20 行ほど）。
- **デプロイ直後の初回起動は特に遅い**: 新しくプッシュしたイメージの初回起動は、ECR から取得し直すため 2B で 7 分ほどかかりました。そこで CloudFormation のカスタムリソースで新しいバージョンを 1 回呼び出してから Gateway を公開するようにしました。この遅延をデプロイ中に吸収できるうえ、モデルが読み込めなければデプロイを失敗させる**スモークテスト**にもなっています。

### 3.4 Lambda の CPU で推論する現実と、arm64 という答え

Lambda には GPU がありません。10GB のメモリを割り当てると 6 vCPU になります。計測結果は次のとおりです（Q4_K_M、日本語 250 文字の段落を英訳、ウォーム状態）。

| モデル | arm64 | x86_64 |
|---|---|---|
| 0.8B | **1.1 秒** | 1.8 秒（生成 58 tok/s） |
| 2B | **2.7 秒**（プロンプト処理 104 tok/s） | 5.5〜7 秒（生成 19 tok/s、プロンプト処理 69 tok/s） |

- x86 では、スレッド数、Flash Attention、バッチサイズを変えても速度はほぼ変わりませんでした。AVX-512 のない CPU の演算性能そのものが上限のようです。
- **arm64 (Graviton) のほうが 1.5〜2.4 倍速く、GB 秒あたりの単価も約 2 割安い**ので、既定値を arm64 にしました。なお、Amazon Linux 2023 の GCC 11 では llama.cpp の armv9.2 向けバリアントをコンパイルできません。arm64 では `armv8.2-a+dotprod+fp16` の 1 種類だけをビルドしています。
- メモリを減らすと vCPU も減って遅くなります。結局リクエストあたりの料金はほぼ同じなので、最大の 10GB を既定にしました。

### 3.5 並列化で 305 秒 → 55 秒

CPU では、2B モデルが 1,024 トークンのチャンクを訳すのに約 55 秒かかります。18KB の Markdown ファイル（3 チャンク）を順番に処理すると **305 秒** でした。

そこで、チャンクを 512 トークンに小さくし、最大 8 本の Lambda で並列に処理するようにしました。結果は **54.6 秒** です（arm64、5 セグメント、コールドスタート込み）。計算量の合計は同じなので、料金はほとんど変わらず、待ち時間だけが短くなります。

一貫性のための工夫もしています。

- **セグメント内では、直前のチャンクの原文と訳文をチャット履歴として渡す**: PLaMo のテンプレートは「原文と訳文の組」を履歴として受け取れるので、PLaMo 専用のコードを書かずに実現できました。
- **履歴はずらさずに伸ばしていく**: 直前の 1 組だけを渡すようにずらしていくと、毎回プロンプトの先頭が変わってしまい、llama-server が前回の計算結果（KV キャッシュ）を再利用できません。コンテキストの半分に収まるあいだは履歴を伸ばし続け、超えたら直近の組からやり直すことで、キャッシュの再利用率を上げました。
- **セグメントの境界をまたぐ用語の統一には `glossary` を使う**。完全に一貫性を優先したい場合は `MaxParallelSegments=1` にすると、全体を順番に処理します。

### 3.6 「委譲すれば安くなる」の落とし穴

最初の設計では、エージェントが本文を `translate(text=...)` に渡す想定でした。しかしよく考えると、**本文を引数として書き出すこと自体が、エージェントの出力トークンを原文の長さだけ消費します**。これでは、エージェントが自分で翻訳するのとあまり変わりません。

本当に安くするには、データそのものではなく**データの場所を渡す**必要があります。ただ、Gateway の後ろにある Lambda からは利用者のディスクが見えませんし、`mcp-proxy-for-aws` はメッセージを中継するだけです。そこでローカルクライアントを自作し、次のように動くようにしました。

- リモートのツールはそのまま中継しつつ、ドキュメント処理に対応したツールには `<ツール名>_file` という派生ツールを**自動生成**する
- どのツールが対象かはリモートの `get_model_info` から判断するので、クライアントもモデルに依存しない
- ファイルは、スタックが作成した S3 バケットとの間で署名付き URL を使って受け渡す

### 3.7 細かいけれど効いた落とし穴

- **Lambda は root 以外のユーザーで実行される**: Dockerfile の `ADD <URL>` で取得したファイルはパーミッションが 0600 になり、読み込めませんでした。ローカルのエミュレータは root で動くので、この問題に気づけません。
- **anyio のキャンセルスコープ**: リモートへの MCP セッションを、あるリクエスト処理のタスクで開いて別のタスクで閉じると例外になります。ツール呼び出しごとに同じタスクの中でセッションを開閉するようにしました。認証情報も毎回新しく読み込まれるので、副次的な利点もありました。
- **関数のデフォルト引数**: `def plan_segments(n, max_parallel=MAX_PARALLEL)` と書くと、関数を定義した時点の値で固定されてしまいます。テストで並列数を差し替えても効かないことから見つかりました。

## まとめと今後

- Hugging Face の GGUF モデルを、YAML 1 枚とワンクリックのデプロイで MCP ツールにできる仕組みを作りました。最初の例は PLaMo 3 Translate です。
- 待機中のコストはゼロで、短い文なら約 2 秒、18KB のドキュメントなら約 1 分・約 0.024 ドルで翻訳できます。
- モデルの成果物（チャットテンプレートと GGUF）を設定の情報源とし、プロファイルには人が判断すべきことだけを書く、という線引きが汎用化の鍵でした。

今後やりたいこと:

- `.docx` や `.html` への対応（分割処理を 1 つ追加するだけで、プロファイルの変更は不要）
- `hf-lambda-mcp init <repo>`: チャットテンプレートと GGUF からプロファイルの雛形を自動生成するコマンド
- 1 つの Gateway の後ろに複数のモデルを並べること、大きなモデル向けの GPU バックエンド

翻訳以外にも、「小さくて得意分野がはっきりしたモデル」は Hugging Face にたくさんあります。フロンティアモデルがまとめ役になり、作業の実行はサーバーレスな小さいモデルが担う。そんな分業を試すきっかけになればうれしいです。
